# Wedding Game

一款用于电子婚礼请柬的竖屏轻量互动小游戏。

玩家以“勇士”的身份协助王子寻找公主，穿越森林、跨越障碍、击败哨兵，并从宝箱中选择一件宝物。抵达城堡后，玩家发现所谓的怪物其实是新人养的猫。故事最后由勇士为王子与公主拍照，照片转化为婚礼迎宾海报，并进入正式请柬。

## 项目定位

这是一个以移动端竖屏浏览器为主要运行环境的互动婚礼请柬。当前版本优先保证单人、轻量、无需登录即可完成体验；项目现在拆分为独立的 `frontend/` 前端游戏和 `backend/` 后端 API 服务。

## 技术架构

### 当前前端

- **页面层**：原生 HTML，负责游戏容器、剧情对话、表单、按钮和最后的迎宾页。
- **样式层**：原生 CSS，负责竖屏布局、移动端安全区域、像素风控件、动画和迎宾照适配。
- **游戏逻辑**：原生 JavaScript，使用 `setScene()` 管理剧情场景和交互状态。
- **画面渲染**：主游戏画面使用 Canvas 绘制角色、森林、障碍、战斗和动画；迎宾照使用 HTML/CSS 展示，避免真实照片被像素化。
- **本地资源**：剧情图片、角色素材和迎宾照统一放在 `frontend/assets/`，随前端项目部署。
- **数据保存**：当前不依赖数据库；勇士名字和游戏过程只存在当前会话中。

前端可以作为静态网站独立部署，例如部署到 GitHub Pages、Vercel、Netlify 或普通 Web 服务器；后端可以独立部署到 Node.js 主机、容器或 Serverless 平台。

### 目录结构

```text
frontend/
  index.html       # 游戏页面
  game.js          # 剧情、状态和 Canvas 渲染
  styles.css       # 页面样式和移动端布局
  assets/          # 迎宾照、像素素材和其他静态资源
backend/
  server.js        # Node.js HTTP API
  package.json     # 后端脚本与运行约束
  .env.example     # 后端环境变量示例
  README.md        # 后端接口说明
docs/              # 故事、交互流程和决策文档
```

### 推荐的后续前后端架构

如果需要长期保存宾客祝福，建议保持前后端分离：

```text
移动端游戏页面
    │
    │ HTTPS / fetch()
    ▼
后端 API 服务
    ├── 数据库：祝福文字、签名记录、时间、状态
    └── 对象存储：手写签名 PNG、合成后的祝福图片
```

前端负责交互、动画、手写采集和图片预览；后端负责数据校验、保存、图片地址管理和后台查询。两者通过 HTTP 请求通信，不需要把后端代码耦合进游戏页面。

部署时可以使用同域名：

```text
https://wedding.example.com/              # 前端游戏
https://wedding.example.com/api/blessings # 后端接口
```

也可以使用独立 API 域名。使用同域名反向代理可以减少跨域（CORS）配置。

## 迎宾照

- 迎宾照：将照片放到 `frontend/assets/` 并命名为 `welcome-photo.png`。照片会自动按屏幕比例完整适配；如果暂时没有照片，海报继续显示像素画兜底。
- 页面每次加载都会为照片请求追加时间戳，替换图片后重新打开页面即可看到新版本。
- 如需使用其他文件名，直接修改 `frontend/game.js` 中 `GAME_CONFIG.welcomePhoto` 的路径。

## 背景音乐

将 MP3 文件放到：

```text
frontend/assets/music/background.mp3
```

页面会尝试自动循环播放背景音乐。由于手机浏览器通常禁止页面在没有用户操作时自动播放，若首次加载被拦截，用户第一次点击、触摸或按键后会自动开始播放。页面不显示音乐开关按钮。

## 计划功能

### 时光相册

最后一页的一个入口将改为“时光相册”。计划采用类似冲洗胶卷的时间轴展示方式：

- 胶卷齿孔和横向时间轴作为视觉主线；
- 照片逐张冲洗，从模糊、低对比度逐渐变清晰；
- 支持左右滑动、上一张/下一张和照片序号；
- 每张照片可以配置日期、地点或简短说明；
- 最后一张提供返回迎宾页的入口。

建议资源目录：

```text
album/
  01.jpg
  02.jpg
  03.jpg
```

建议相册照片统一使用 `4:3` 或 `3:2` 比例，单张宽度不低于 `1200px`。照片数量建议先控制在 `6–12` 张，以保证移动端加载速度。

### 祝福签名

另一个入口将改为“祝福签名”。计划提供一个游戏风格的签名板，而不是直接调用浏览器原生弹窗：

- 支持触摸、鼠标和手写笔输入；
- 支持手写签名和打字祝福两种方式；
- 支持清除、撤销和重新输入；
- 用户提交后，在横版迎宾照上拖动或选择签名位置；
- 使用 Canvas 合成照片、文字和签名；
- 支持预览、下载和分享最终图片。

第一版可以只在浏览器本地完成合成，不需要后端。若需要新人集中查看所有祝福，再接入后端 API 保存数据。

## 后端接口规划

后端不是当前运行所必需的，只有需要长期保存或集中管理祝福时才接入。建议从以下接口开始：

```text
POST /api/blessings       # 提交祝福文字、签名和位置
GET  /api/blessings       # 管理端查询祝福列表
GET  /api/blessings/:id   # 查看一条祝福
POST /api/blessings/:id/render # 生成最终合成图片（可选）
```

前端提交的数据可以采用以下结构：

```json
{
  "text": "祝你们永远幸福",
  "signatureUrl": "https://storage.example.com/signatures/abc.png",
  "position": { "x": 0.72, "y": 0.84 },
  "createdAt": "2026-09-18T12:00:00.000Z"
}
```

建议将签名 PNG 和最终合成图片放在对象存储，将文字、图片地址、位置、时间和审核状态放在数据库。后端需要限制文字长度、图片大小和提交频率，并根据实际部署方式配置 CORS。

## 资源约定

- 迎宾照：`frontend/assets/welcome-photo.png`。
- 相册照片：建议放在 `album/` 目录，并按顺序命名。
- 像素参考素材：放在 `frontend/assets/`，避免在代码中散落路径。
- 用户上传内容：未来接入后端后，不直接写入前端项目目录，统一交给对象存储管理。

## 本地运行

前端和后端需要分别启动。先启动前端静态服务：

```bash
cd frontend
python3 -m http.server 4173
```

另开一个终端启动后端 API：

```bash
cd backend
npm start
```

然后访问前端：

```text
http://127.0.0.1:4173/
```

后端健康检查地址：

```text
http://127.0.0.1:8787/health
```

不要直接通过 `file://` 打开，因为浏览器对本地文件的图片加载、缓存和部分交互行为存在限制。

## 前端性能说明

- 相册缩略图使用懒加载和异步解码，不会在打开相册时强制加载所有照片。
- 相册当前照片优先加载，切换照片时复用浏览器缓存；静态资源不再为每次切换追加新的时间戳。
- 进入迎宾页、相册或签名页后，游戏 Canvas 主循环暂停绘制，避免后台持续消耗 CPU。
- 当前相册仍使用原始照片文件；正式发布前建议生成缩略图和 WebP/AVIF 版本，时间轴使用缩略图，查看大图时再加载原图。
- 相册照片总量较大时，优先优化图片格式和尺寸，再考虑 CDN、断点加载和分页。
